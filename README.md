**# Тема: Маркетплейс вещей
## 1. Описание предметной области

Проект представляет собой маркетплейс одежды, обуви и аксессуаров.  
В системе есть пользователи (покупатели), продавцы (отдельные магазины) и администраторы.  

Продавцы размещают товары в каталоге. Каждый товар имеет варианты (SKU), определяемые набором атрибутов (размер, цвет и т.п). Цена и остатки ведутся на уровне SKU. Остатки хранятся по складам продавцов.

Покупатели формируют корзину и оформляют заказ. Один заказ может содержать товары от разных продавцов, поэтому внутри общего заказа формируются подзаказы по каждому продавцу.  

Для подзаказов и отправлений хранится история смены статусов. Оплата оформляется как отдельная сущность на уровне общего заказа. Доставка осуществляется отдельными отправлениями по подзаказам продавцов.

---

## 2. Функциональные требования

- В системе есть пользователи с ролями: покупатель, продавец, администратор.
- Пользователь может иметь несколько ролей.
- Продавец — это отдельный магазин, связанный с учетной записью пользователя.
- Продавец размещает товары.
- Товар имеет несколько вариантов (SKU), определяемых набором атрибутов (размер, цвет и т.п).
- Цена фиксируется на уровне SKU.
- Остатки ведутся по складам продавца.
- Пользователь имеет корзину с позициями.
- Заказ может содержать товары нескольких продавцов.
- Для каждого продавца внутри заказа создается отдельный подзаказ.
- Для подзаказов ведется история смены статусов.
- Оплата осуществляется на уровне общего заказа.
- Один заказ может иметь несколько попыток оплаты.
- Доставка осуществляется отдельными отправлениями по каждому подзаказу.
- Для отправлений хранится история статусов доставки.

---

## 3. Бизнес-правила

- Email пользователя уникален.
- Пользователь может иметь несколько ролей. Это реализовано через таблицу связей user_roles.
- Продавец связан с одной учетной записью пользователя, т.е user_id уникален в sellers.
- SKU уникален по своему коду (sku_code).
- Комбинация (warehouse_id, sku_id) в таблице inventory уникальна.
- Комбинация (order_id, seller_id) в таблице seller_orders уникальна.
- В order_items хранится unit_price — цена на момент покупки.
- Суммы заказов и подзаказов не хранятся в БД, а вычисляются запросами.
- История статусов заказов и отправлений хранится отдельными записями.
- Заказ ссылается на конкретный адрес пользователя.
- В таблице sku_attribute_values дополнительно хранится attribute_id для обеспечения ограничения, чтобы у одного SKU было не более одного значения для каждого атрибута. Это реализовано через уникальность (sku_id, attribute_id).
- В таблице order_items реализована уникальность пары (seller_order_id, sku_id). Это исключает дублирование одной и той же позиции в пределах подзаказа.

## 4. Описание модели

### Основные сущности

- users — учетные записи
- roles — роли
- user_roles — роли пользователей
- addresses — адреса пользователей
- sellers — магазины-продавцы
- products — товары
- skus — варианты товаров (SKU)
- attributes — атрибуты (размер, цвет и т.п)
- attribute_values — значения атрибутов
- sku_attribute_values — связь SKU и значений атрибутов
- warehouses — склады продавцов
- inventory — остатки SKU на складе
- carts — корзины
- cart_items — позиции корзины
- orders — общий заказ
- seller_orders — подзаказы по продавцам
- order_items — позиции подзаказа
- order_statuses — справочник статусов
- seller_order_status_history — история статусов подзаказа
- payment_methods — способы оплаты
- payment_statuses — статусы оплаты
- payments — попытки оплаты
- delivery_services — службы доставки
- shipments — отправления
- shipment_statuses — статусы доставки
- shipment_status_history — история статусов доставки

### Основные связи

- users 1—N addresses  
- users N—M roles (через user_roles)  
- users 1—0..1 sellers  
- sellers 1—N products  
- products 1—N skus  
- attributes 1—N attribute_values  
- skus N—M attribute_values (через sku_attribute_values)  
- sellers 1—N warehouses  
- warehouses 1—N inventory  
- skus 1—N inventory  
- users 1—N carts  
- carts 1—N cart_items  
- skus 1—N cart_items  
- users 1—N orders  
- orders N—1 addresses  
- orders 1—N seller_orders  
- sellers 1—N seller_orders  
- seller_orders 1—N order_items  
- skus 1—N order_items  
- seller_orders 1—N seller_order_status_history  
- order_statuses 1—N seller_order_status_history  
- orders 1—N payments  
- payment_methods 1—N payments  
- payment_statuses 1—N payments  
- seller_orders 1—N shipments  
- delivery_services 1—N shipments  
- shipments 1—N shipment_status_history  
- shipment_statuses 1—N shipment_status_history

## 5. Нормализация до 3НФ

- Все сущности имеют первичный ключ.
- Повторяющихся групп нет.
- Роли, статусы, методы оплаты, службы доставки вынесены в отдельные таблицы.
- История статусов хранится отдельными сущностями.
- Суммы заказов не хранятся, а вычисляются запросами.
- В схеме отсутствуют транзитивные зависимости неключевых атрибутов от первичного ключа.
